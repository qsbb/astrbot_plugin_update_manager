# 系列接管页 UI 方案综合评审与 D3 改良规格

> 日期：2026-09-14  
> 结论：盲测数据第一是 **09 / D2**，不是 08 / D3；D3 三人总分 67，位列 9 个方案第 8，只高于 06 / C 的 62。但用户明确偏好 D3 的主从骨架，因此推荐基线定为 **D3.1 = D3 主从 + 双列能力网格 + D2 的管理闭环 + B3 的能力预览思路**。  
> 依据：用户提供的三人评分与 D3 五条共同批评；仓库中已实现的 `webui/app.js`、`webui/style.css`、`core/capability_catalog.py`、`tests/test_pages_ui.py` 与 `docs/TAKEOVER-UI-D3-SPEC.md`。  
> 边界：本报告只做综合评审与规格建议；本次未修改代码、未修改既有规格、未提交任何内容。

---

## 0. 决策摘要

1. **D2 第一来自“管理闭环在静态画面里完整可见”**：能力行、状态文字、明确设置列、异常排序共同回答了“是什么、现在怎样、去哪里处理、先处理谁”四个问题。28/26/27 的稳定高分说明它不是靠某一位评审的偏好取胜。
2. **D3 靠后不等于主从 + 网格被否决**：Goodall 仍给了 24，说明骨架有吸引力；但 Descartes 23、Halley 20，且 Halley 排名最后，说明当前静态表达没有把交互优势转成可见价值。五条批评中，四条是真实设计缺陷，一条包含明显的截图误差。
3. **不能用“用户偏好”直接抵消可用性缺口**：正确做法是保留 D3 的空间连续性、同屏上下文和双列卡片，把 D2 的“状态文字、明确动作、异常优先”压缩进卡片内部，而不是再加一个 D2 式操作列。
4. **D3.1 的放行条件不是“看起来像 D2”**：而是在不看规格、不悬停、不点击的静态截图中，评审仍能一眼认出每张卡状态与操作、知道异常为何排前、知道一个来源为什么不值得重复显示，并能看出域名下列有哪些能力。
5. **最低业务门槛**：五条批评全部有截图为证；“来源 1 个模块”在样例中不再出现；状态不再只靠色点；1440/1024/720/560/390 均无横向溢出；复测不再出现任一评审低于 24 的静态可读性问题。未达门槛时，D2 的管理结构作为降级基线，而不是继续用“交互里其实能点”解释。

### 1.2 D2 为什么第一

D2 的四个可见构件形成了完整管理闭环：

1. **能力行**：用户先看到可管理的对象，而不是先猜卡片能否点击。
2. **状态文字**：不只显示绿/黄/灰色点，因此截图和触屏场景都不依赖悬停标题。
3. **设置列**：每行的操作目标明确且重复一致，扫视成本低。
4. **异常优先排序**：把“先处理谁”变成页面默认行为，管理页从浏览视图升级为处理队列。

因此，D2 的高分不是“信息最多”，而是**信息在静态图中可自解释**。Goodall 28、Descartes 26、Halley 27 说明这种自解释性跨评审稳定。

### 1.3 D3 为什么靠后

D3 的五条共同批评可以归成三个根因：

| 根因 | 对应批评 | 影响 |
|---|---|---|
| 操作闭环缺失 | ① 能力卡没有明确操作目标；② 来源文案没信息价值 | 用户看得到能力，却看不出点哪里、点了能得到什么 |
| 信息密度失衡 | ③ 卡片信息薄、留白多，40 项能力需更多滚动 | 卡片占用面积没有被有效信息填满，浏览成本上升 |
| 响应式与语义不足 | ④ 双栏窄屏难压缩；⑤ 状态点缺语义 | 小屏不成立，状态无法被色觉障碍用户或静态图读者理解 |

Goodall 的 24 分说明 D3 的主从骨架、域与能力同屏确有价值；Halley 的 20 分说明仅靠布局优势不足以抵消以上根因。

### 1.4 三人共识与分歧

**共识：**

- D2 的管理闭环最强：三人分别给出 28、26、27，且两人第 1、一人第 3。
- D3 明显低于 D2：每人分差 4、3、7，总分落后 14。
- 01 / D 和 03 / E、07 / B3 处在稳定前列；06 / C 被三人一致压在末位（20、20、22）。
- 05 / B2 的状态数量表达清晰，但三人均给 23，说明“清楚”没有转化成明显优势。

**分歧：**

- Goodall 对 D3 的 24 分说明主从 + 网格的视觉方向可保留；这不是全盘否定。
- Descartes 的 23 分更像“可用但不完整”，不是末位。
- Halley 的 20 分显示其评价权重更偏向静态动作入口、状态语义和窄屏成立性。
- 对比 01 / D 的 25、27、25 可推断：没有操作列并非必然失败；真正的问题是 D3 同时缺少明确动作提示与状态文字，导致主从布局的上下文优势没有被转化为管理效率。

### 1.5 方案缺陷与“静态截图看不到交互”的误差

| 观察 | 分类 | 判定 |
|---|---|---|
| 能力卡没有“设置”或箭头 | **真实缺陷 + 截图放大** | 整卡可点并不等于用户知道可点；截图看不到 hover，但缺少可见入口仍然成立于真实产品 |
| “来源 1 个模块”重复 | **真实内容缺陷** | 目录 40 项中 30 项为单来源、7 项为核内治理入口、仅 3 项为双来源；单来源数量几乎全是噪声 |
| 卡片信息薄、留白多 | **真实布局缺陷** | 现规格卡内只有名称和来源；即使交互可用，首屏信息利用率仍低 |
| 高密度双栏窄屏难压缩 | **真实响应式缺陷** | 核 WebUI 桌面还有 232px 导航、窄桌面为 196px；只按 900px 视口切布局会误判真实内容宽度 |
| 状态点缺文字/图例 | **真实语义与无障碍缺陷** | `title` 在触屏和截图中都不可见，颜色也不能单独承担状态语义 |
| 整卡点击、键盘、吸附、域切换无法从截图评分 | **截图误差** | 不能把“截图未显示交互”直接判成“交互不存在”；但设计必须在静态层给出足够线索 |
| “40 项都要滚动” | **部分截图误差** | 主从页一次只展示一个域，最大是“对话与消息”的 10 项，不是 40 项；不过 10 项卡片仍应控制在 5 行左右 |
| 异常优先排序没有得分 | **可见性缺陷** | 规格中有排序不等于截图中成立；默认排序、当前排序状态和异常数量必须同时可见 |

原则：**交互存在性**可以在实现验收中核验；**交互可见性**必须在静态评审中核验。D3 当前失败的多数是后者。

## 2. 推荐基线：D3.1

### 2.1 明确取舍

推荐走 **D3.1**，而不是切回 D2，也不是原样发布 D3：

```text
D3 骨架（不可丢）              必须吸收                        B3 思路
┌域导航 + 能力网格同屏┐   ┌状态文字 + 设置动作 + 异常排序┐   ┌域下前 3 能力预览┐
│双列卡片、视觉连续    │   │D2 的管理闭环                │   │域名旁直接可见  │
└────────────────────┘   └─────────────────────────────┘   └────────────────┘
```

**D2 强制吸收的三件事：**

1. **状态文字化**：颜色点升级为“图例符号 + 文字 + 色彩”的状态徽标；域行和能力卡都显示文字。
2. **操作显式化**：每张能力卡固定出现 `设置 ›`；核内治理能力显示 `打开 ›`；整卡点击仍保留，但不作为唯一提示。
3. **异常处理排序化**：默认 `先看需处理 (N)`，用严重度排序；数量为 0 时显示“本域无需处理”并回到目录顺序。

**B3 强制吸收的一点：**

- 域导航不再只给“10 项能力”数字，而是增加一行前三个能力名 + `+N`；窄屏选中 chip 展开显示前两个能力名 + `+N`。预览是常驻信息，不再只放在 hover tooltip 里。

### 2.2 如何兼容用户对 D3 的偏好

- **保留空间关系**：左域、右能力，滚动域列表时能力区不被整体替换；这仍是 D3 的识别特征。
- **保留双列卡片**：不增加 D2 式右侧操作列，不把卡片压成单行表格。
- **保留轻量视觉**：卡片继续使用白/玻璃表面、10px 圆角和轻阴影；只有异常项使用琥珀/红色强调。
- **只在卡片内部升级**：动作、状态、说明、元信息都放进现有卡片，不新增横向列。
- **把用户偏好设为方向票，不设为免测票**：D3.1 先达到静态可读性门槛，再做用户 A/B 偏好复测；若 D3.1 同时满足管理闭环与偏好选择，就无需退回 D2。

## 3. D3.1 改良规格（可直接实现）

### 3.1 总体布局与响应式

现有 D3 规格以 1200 / 900px 视口为主要断点，但核 WebUI 的桌面导航占 232px（`<=1000px` 时 196px），内容区还有约 44–68px 内边距。断点应按内容容器计算。

- 在 `.control-master` 上设置 `container-type: inline-size`，同时保留视口媒体查询作为旧浏览器兜底。
- 桌面主从栅格：`grid-template-columns: 208px minmax(0, 1fr); gap: 12px; align-items: start`。
- 能力网格：`grid-template-columns: repeat(2, minmax(260px, 1fr)); gap: 8px 10px`。
- 域列表：`position: sticky; top: 12px`。

| 内容容器宽度 | 域导航 | 能力区 | 卡片宽度预期 |
|---:|---|---|---|
| `>= 840px` | 固定左栏 208px | 2 列 | 306px 以上 |
| `560–839px` | 顶部横向 chips，sticky | 2 列，单列最小 240px | 276–415px |
| `360–559px` | 顶部横向 chips，sticky | 1 列 | 完整内容宽 |
| `< 360px` | 顶部横向 chips | 1 列，左右 10px | 完整内容宽 |

关键结果：

- 1440px 视口约为 1140px 内容宽，左栏 208px，右区约 920px，双列卡片约 455px。
- 1024px 视口约为 724px 内容宽，切为顶部 chips + 双列，每卡约 358px；避免“196px 左栏 + 双列”被硬挤。
- 720px 以下已有壳层移动导航，内容约 692px，仍可双列；约 560px 以下才单列。
- 390px 下内容约 362px，单列、无横向滚动。

横向 chips：

- `display:flex; gap:6px; overflow-x:auto; scroll-snap-type:x proximity; position:sticky; top:0; z-index:3; padding:6px 0; background:var(--canvas)`。
- chip 最小高度 40px；未选中显示“域名 + 数量”；选中 chip 用两行，第二行显示前两个能力名 + `+N`。
- 选中后调用 `scrollIntoView({inline:"nearest", block:"nearest"})`；容器宽度变化不得重置 `selectedDomain`。

### 3.2 能力卡：固定三行，最小 76px

能力卡从现规格的两行、约 56px，改为 **三行、`min-height:76px`**。在单列窄屏允许第二行换为两行，`min-height:88px`。不增加第四行。

```text
[● 统一接管] 沉默判断                              设置 ›
判断这条消息要不要回、什么时候不回。
2 项可调
```

| 行 | 高度/排版 | 内容 |
|---|---:|---|
| 第 1 行 | 18px；标题 13px/600 | 状态徽标 + 能力名；右侧常驻动作 `设置 ›` 或 `打开 ›` |
| 第 2 行 | 18px/单行；12px | 能力描述；超长省略，`title` 保留全文；390px 下最多两行 |
| 第 3 行 | 16px；11px | 可调项/来源/核内置等有效元信息；不超过 1 行 |

实现参数：

- 卡片：`padding:9px 11px; border:1px solid var(--line); border-radius:10px; background:var(--surface); display:grid; gap:4px; align-content:space-between`。
- 悬停：边框 `#c7d2fe`，背景 `#fbfdff`，阴影 `0 6px 18px rgba(79,70,229,.08)`；不上下位移。
- 键盘焦点：`box-shadow:0 0 0 3px rgba(37,99,235,.22)`；卡片本身是按钮时不得嵌套第二按钮。
- 动作：`设置/打开` 使用 11px/700、`#4338CA`，加 `›`；桌面最小命中区 44×32px，移动端 44×44px。
- 动作与整卡点击目标一致。动作是一个 `<span>` 视觉提示，不制造嵌套交互。
- 无 provider、无 view 的兜底卡不显示假按钮，显示 `暂无入口`，卡片不可点击。

动作映射：

| 条件 | 卡片右上动作 | 点击结果 |
|---|---|---|
| `providers.length > 0` | `设置 ›` | 打开该能力详情，仅展示该能力的字段集合 |
| `providers.length = 0 && views.length > 0` | `打开 ›` | 进入核内治理视图 |
| 其他 | 无动作 | 显示 `暂无入口`，禁用点击 |

### 3.3 第 3 行文案：“来源 N 个模块”替换矩阵

目录事实：40 项能力中，30 项为单来源、7 项为核内治理入口、3 项为双来源；单来源里 20 项有字段、10 项没有字段。因此“来源 1 个模块”几乎必然重复。

| 数据条件 | 第 3 行文案 | 示例 |
|---|---|---|
| 1 个 provider，有字段 | `{字段总数} 项可调` | `2 项可调`、`4 项可调` |
| 1 个 provider，无字段 | `在模块里设置` | `在模块里设置` |
| 2 个 provider，有字段 | `{N} 个模块共同提供 · {字段总数} 项可调` | `2 个模块共同提供 · 12 项可调` |
| 2 个 provider，无字段 | `{N} 个模块共同提供 · 在模块里设置` | `2 个模块共同提供 · 在模块里设置` |
| 无 provider，有 view | `核自带` | `核自带` |
| 无 provider，无 view | `暂无可用入口` | `暂无可用入口` |

规则：

- `字段总数 = Σ capability.providers[].fields.length`，不临时请求 schema；目录已有该数据。
- 单来源永远不显示“1 个模块/1 个来源”。
- provider 名称只在能力详情的“来源”折叠区出现，卡片不暴露模块名。
- 多来源信息只在 N≥2 时显示，因为它确实解释“为什么一个能力可能由多个设置分区组成”。

具体卡面示例：

```text
[● 统一接管] 拟人化情绪                     设置 ›
回复意愿会随互动变化：偶尔懒散、烦躁或不想回。
2 个模块共同提供 · 12 项可调
```

```text
[◌ 核自带] 更新与回滚                        打开 ›
更新、回滚与恢复点的统一入口。
核自带
```

### 3.4 状态文字、符号与图例

状态必须同时具备 **形状 + 文字 + 颜色**。颜色只做冗余强化，不得是唯一语义。

#### 能力/域状态映射

| 内部状态 | 触发条件摘要 | UI 文案 | 前景/背景 | 圆点/形状 | 严重度 |
|---|---|---|---|---:|---:|
| `ready` | 全部 provider 已统一接管 | `统一接管` | `#166534 / #ECFDF3` | `● #22C55E` | 5 |
| `partial` | 统一接管模式下有 provider 未纳入 | `部分待接管` | `#B45309 / #FFFBEB` | `▲ #F59E0B` | 1 |
| `degraded` | 已知运行降级 | `运行降级` | `#B45309 / #FFFBEB` | `▲ #F59E0B` | 1 |
| `unavailable` | 部分/全部 provider 未加载或不可用 | `部分不可用` / `不可用` | `#B91C1C / #FEF2F2` | `■ #DC2626` | 0 |
| `stale` | 超过 180 秒未刷新 | `数据可能过期` | `#0369A1 / #F0F9FF` | `◐ #0284C7` | 2 |
| `unknown` | 状态缺失或无法判定 | `待检查` | `#52525B / #FAFAFA` | `? #A1A1AA` | 3 |
| `native` | 独立配置模式下全部 provider 为 native | `独立设置` | `#475569 / #F1F5F9` | `○ #94A3B8` | 4 |
| `core` | 无 provider 的核内入口 | `核自带` | `#475569 / #EEF2FF` | `◇ #6366F1` | 5 |

关键语义修正：

- `独立设置` 在全局模式为独立配置时不是错误，不进入异常数量。
- 只有全局模式为统一接管，而能力仍有 native provider 时，才显示 `部分待接管` 并计入异常。
- `数据可能过期` 与 `待检查` 分开，前者是新鲜度问题，后者是状态缺失问题。
- 域状态取域内能力最严重状态；域行同样显示文字，不能只放一个色点。

#### 图例

模式条右侧或第二行固定显示：

```text
状态：● 统一接管   ▲ 待处理/降级   ■ 不可用   ◐ 数据可能过期   ○ 独立设置   ◇ 核自带
```

- 桌面常驻一行，11px，允许换行。
- 390px 下放入“状态说明”折叠区，默认摘要显示 `统一接管 / 待处理 / 不可用 / 数据过期` 四类。
- 每张卡的 `aria-label` 使用 `"{能力名}：{状态文案}"`。
- 不使用只在 `title` 中出现的状态说明；触屏和截图均不可依赖 hover。

### 3.5 异常优先排序

`异常优先` 改名为 `先看需处理`；右侧分段控件为：

```text
[ 先看需处理 (2) ] [ 默认顺序 ]
```

规则：

1. 默认选中 `先看需处理`，但只在当前域异常数 `N > 0` 时真正重排。
2. `N = 0` 时显示 `本域无需处理`，视觉上保持目录顺序，不制造无意义重排。
3. 只重排当前域的能力网格；域列表保持目录顺序，避免用户选中一个域后该域突然跳到别处。
4. 严重度顺序：`unavailable(0) > partial/degraded(1) > stale(2) > unknown(3) > native(4) > ready/core(5)`。
5. 同级排序：受影响 provider 数降序 → 目录原始顺序升序。不要按中文名称排序，避免状态刷新时产生难以追踪的跳位。
6. 排序为纯派生值，不修改 catalog；`selectedDomain`、`selectedCapability`、键盘焦点必须跨重排保持。
7. 切换域后能力区滚动到网格顶部；排序偏好只保存在当前会话内存。
8. 动画仅使用 120ms 的 `transform/opacity`；`prefers-reduced-motion: reduce` 时禁用。

设计原因：D2 因“异常优先”得到高分，但若控制项不在首屏、没有数量或看不出排序结果，静态评审实际不会给分。D3.1 必须把“默认策略 + 待处理数量 + 当前选中状态”同时放在模式条上。

### 3.6 B3 能力预览：放进域导航，不再依赖 tooltip

桌面域项为两行、最小高度 56px：

```text
💬 对话与消息                         10 项   ●统一接管
沉默判断 · 智能分段 · 插话合并 +7
```

参数：

- 第 1 行：图标 + 域名 13px/600 + 数量 11px + 状态文字 10.5px。
- 第 2 行：11px muted，前三个能力名，中点分隔，末尾 `+N`；单行省略。
- 预览顺序：有异常时先列异常能力，再按目录顺序；无异常时按目录顺序。
- 域列表选中态：`background:var(--si-primary-soft); color:var(--si-primary-strong); border-left:3px solid var(--si-primary)`；内边距相应减 3px，防止文字偏移。
- 桌面 7 项域列表约 `7×56 + 6×4 = 416px`，仍能在 900px 高页面首屏附近完整看到。
- 窄屏未选中 chip 一行，选中 chip 两行并显示前两个能力名 + `+N`；预览从 hover-only 改为常驻、键盘和触屏均可达。
- 预览只回答“这个域里有什么”，不重复展示能力描述和状态徽标，避免变成 B3 的整页域瓦片。

### 3.7 键盘、触屏与语义

- 域容器：`role="tablist"`；域项 `role="tab"`、`aria-selected`、roving tabindex；`↑/↓/Home/End` 切换，`Enter/Space` 保持选择。
- 能力网格：每卡一个可聚焦按钮；`Enter/Space` 打开；焦点环 3px，对比度不小于 3:1。
- `先看需处理/默认顺序`：使用 `role="group"` + `aria-pressed`，可用左右方向键切换。
- 状态徽标需有可见文字和 `aria-label`；颜色不作为唯一状态信号。
- `设置` 只显示该能力的字段；详情返回后恢复原域、原排序与原焦点。
- 移动端所有动作命中区至少 44×44px；正文不得小于 11px，设备像素比下至少 1px 边框。
- 域切换不发起新网络请求；只有进入能力详情才按 provider 拉取 schema/snapshot。

## 5. 落地顺序与补充验收

### 5.1 落地顺序

**P0-A：状态语义和文案单一事实源**

- 增加 `statusMeta()`：输出 `key/label/symbol/colors/rank/ariaLabel`。
- 增加 `capabilityMetaText()`：实现第 3.3 节矩阵。
- 先补单测，再替换域行、能力卡、图例中的零散判断。
- 目的：先消灭色点无语义和“来源 1 个模块”两个确定性缺陷。

**P0-B：卡片结构与管理闭环**

- 卡片改为三行，加入常驻 `设置/打开` 动作和描述行。
- `<button>` 卡片内不嵌套按钮；无入口卡片不可点击。
- 检查动作焦点、Enter/Space、返回焦点恢复。
- 目的：同时回应批评 ① 和 ③。

**P0-C：异常优先排序**

- 增加 `sortCapabilities()` 和 `attentionCount`。
- 模式条显示 `先看需处理 (N)` / `默认顺序`；N=0 保持目录顺序。
- 排序前记录焦点 ID，排序后恢复；域列表不重排。
- 目的：吸收 D2 最强的管理闭环。

**P1-A：B3 域预览**

- 增加 `capabilityPreview(domainId, max=3)`；异常优先、其余按目录顺序。
- 桌面域项第二行常驻；窄屏选中 chip 两行。
- 目的：吸收 B3 的可预知性，不复制 B3 的整页域瓦片。

**P1-B：容器查询与窄屏**

- 在主从容器上加 `container-type`，实现 840 / 560 两个内容宽度断点。
- 卡片最小 240px；滚动容器统一 `min-width:0`；文本 `overflow-wrap:anywhere`。
- 在 1024、900、720、560、390 做浏览器截图回归。
- 目的：回应批评 ④。

**P2：视觉打磨与盲测复测**

- 只保留 hover/focus 动效、选中过渡和 sticky 细节，不再增加信息结构。
- 用同一组截图让评审重点复看五条批评是否消失。
- 若复测仍出现任一评审低于 24 的“静态可读性”问题，回退到 D2 管理结构；若没有，D3.1 作为最终基线。

| **排序导致空间记忆丢失** | 状态刷新后能力卡大范围跳位 | 只重排当前域；同级按目录顺序；未处理项不重排；焦点 ID 恢复 |
| **窄屏过早单列** | 仅因视口 <900px 就单列，内容拉长 | 使用容器查询；560–839px 保持双列；<560px 才单列 |
| **触屏语义退化** | `title`、hover、整卡点击在手机上不可发现 | 常驻动作和状态文字；选中 chip 展开预览；命中区 44px |
| **误导性字段数量** | 多 provider 重复字段被计成双份 | 统一在 `capabilityMetaText()` 中定义计数口径并补单测；宁可显示“有可调设置”也不虚报 |
| **静态评审继续低估 D3** | 交互功能真实存在，但截图中不可见 | 默认状态、排序结果、图例、动作全部常驻；先做静态验收再做交互验收 |
| **偏好压倒证据** | 用户喜欢 D3，就忽略 67 分与五条批评 | 偏好只决定“保留哪套骨架”；D2 的管理闭环作为硬性功能门槛 |
| **范围膨胀到后端契约** | 为了预览和排序新增接口，拖慢 P0 | D3.1 全部由现有 catalog + member status 派生；后端契约不变 |

### 最后应保住的 D3 视觉优势

- **同屏上下文**：左侧始终知道“我在哪个域”，右侧始终看到该域全部能力。
- **双列扫视**：1440 和大多数桌面宽度保持双列，异常项和正常项可以成组比较。
- **卡片而不是表格**：描述和元信息形成轻量阅读节奏，不回到 D2 的高密度管理表。
- **克制的色彩**：正常状态是安静的绿色/灰色，只有待处理和不可用使用琥珀/红色，异常因此更有重量。
- **连续的空间记忆**：域列表不因异常重排，能力区状态排序可恢复焦点；返回详情后仍回到原位置。

最终判断标准不是“D3 得分是否超过 D2”，而是：**保留 D3 的主从空间结构，同时让 D2 的管理闭环不依赖交互说明就能被看见。** 达到这一点，用户偏好与盲测证据才能同时成立。
