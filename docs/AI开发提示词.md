# AstrBot 自动更新插件 AI 开发提示词（历史设计归档）

> **归档声明（2026-07-27）**：本文是早期开发提示词，仅供历史追溯，不是当前实现规范，不应直接交给 AI 继续指导当前实现。当前事实以插件根目录 `README.md`、`metadata.yaml`、`main.py`、`core/`、`pages/` 和测试代码为准；若需制定新方案，应基于当前代码重新审计。
>
> 用途（历史）：把本文整体交给 AI，指导其在后续任务中分阶段开发完整插件。本文不是项目代码，也不授权跳过阶段门槛。

## 1. 开工前强制阅读

你将开发 AstrBot 插件 `astrbot_plugin_update_manager`。开始任何设计或编码前，必须按顺序完整阅读并遵循：

1. 公共现行规范：[`../CONVENTIONS.md`](../CONVENTIONS.md)（本仓库根目录）；这是唯一现行系列规范。
2. 详细开发规划：[`开发规划.html`](开发规划.html)。
3. 规范基线快照：[`CONVENTIONS-公共规范快照.md`](CONVENTIONS-公共规范快照.md)；它只用于追溯，若与公共规范冲突，以公共现行规范为准。

先输出阅读确认、约束摘要、待确认决策和本阶段计划；未读完不得写代码。公共规范或目标 AstrBot API 有变化时，先报告差异并更新方案，禁止静默沿用快照。

## 2. 固定项目身份

- 插件目录名、`metadata.yaml.name`、`@register` 唯一识别名：`astrbot_plugin_update_manager`。
- 系列展示名：`凝心溯溪-核`（“核”代表系列插件的更新管理核心）；稳定插件 ID、目录名与仓库名不得随展示名变化。
- `display_name`：`凝心溯溪-核`。
- `desc` 与 `short_desc` 以“凝心溯溪系列更新模块：”开头，保持工程文档语气。
- 初始版本：`0.1.0`，三段式、无 `v` 前缀。
- AstrBot 支持范围：`>=4.16,<5`。凡使用更高版本才提供的 API，必须提高下界或提供经过测试的能力探测与兼容降级；禁止虚报兼容。
- Python 版本与部署方式以该 AstrBot 支持范围的官方矩阵为准。
- 管理命令拟使用独立前缀 `/aup`；实现前检查同目录插件命令占用，发现冲突先报告。

## 3. 开发目标与边界

开发面向 AstrBot 管理员的完整自动更新插件：发现可管理插件及候选版本，解释更新资格；支持只读检查、冻结计划、手动选择性串行更新、每日规则、审计、备份、健康检查和失败回滚。优先复用 AstrBot 核心更新能力，通过单一 `AstrBotAdapter` 隔离非稳定接口，不从插件内部调用 Dashboard HTTP 管理端点。

仅管理 AstrBot 插件，不更新 AstrBot 本体、Python、Docker 镜像、操作系统或本插件自身。默认只检查；自动规则默认关闭，并且只作用于管理员显式选择的插件。新安装插件不得静默加入规则。

## 5. 分阶段执行

严格遵循开发规划第 14 节：

1. **阶段 0，兼容性探针**：固定目标 AstrBot tag/commit，验证 PluginManager、安装源、reserved/禁用状态、reload、cron 和卸载行为；产出适配器契约与测试，不做正式更新功能。
2. **阶段 1，只读检查与计划**：实现 catalog、候选读取、PEP 440、资格解释、缓存/限流、不可变计划及管理员只读命令；绝不修改插件。
3. **阶段 2，手动受控更新**：实现同一 coordinator、全局互斥、插件级备份、官方核心更新调用、健康检查、审计、自动回滚和手动多选；并发度固定为 1。
4. **阶段 3，每日规则**：实现规则持久化、IANA 时区、jitter、misfire、启动恢复、revision、防重复 job、预演和通知；默认关闭。
5. **阶段 4，稳健性扩展**：发布年龄、摘要、容量/保留、人工回滚和通知扩展；是否有限并发必须由数据和新增测试证明。

每阶段都必须先列变更计划，再实现最小闭环，运行本阶段全部测试，提交阶段报告；只有门槛全部通过且无未解决高风险问题，才可进入下一阶段。不得一次性生成全部代码后再补测试。

## 6. 功能与实现约束

- 使用 `packaging.version.Version`、`SpecifierSet` 或等价 PEP 440 实现；禁止字符串比较版本。
- 计划包含过期时间、AstrBot 版本、来源证据、规则 revision、目录/版本指纹和 plan hash；执行前重新校验，目标变化即阻断。
- 一个插件一个事务；批次中单项失败按策略回滚并继续或停止，状态不得伪造不可观测步骤。
- 手动与定时更新必须走同一 coordinator；进程内锁与跨进程锁都要有测试。
- 更新前保持 activated/disabled 状态，更新后不得擅自启用原本禁用的插件。
- `terminate()` 必须清理定时任务、网络客户端、文件句柄、动态工具和模块级实例。
- 配置 Schema 每项必须有类型、描述和默认值；密钥按 AstrBot 秘密配置能力处理。
- 网络请求必须异步，具备合理 timeout、条件请求、缓存、限流感知、退避和代理兼容。
- 若无法可靠获得来源、版本、兼容范围或权限，明确标记不可自动更新，不得猜测。

## 7. 安全要求

- 只接受插件已记录的 market/GitHub 来源；固定规范化 owner/repo，不允许页面/API 传任意本地路径或任意仓库执行更新。
- 管理写操作必须验证管理员权限，并采用 AstrBot 可用的同源/CSRF 防护；所有输入做 schema、长度、枚举和路径校验。
- 对插件根目录、data、备份和恢复目标执行 `realpath` containment；拒绝软链接逃逸、路径穿越和未经本插件生成且摘要不匹配的备份。
- token、请求头、绝对敏感路径和隐私数据不得进入日志、审计或异常回显；日志需脱敏。
- 记录来源 URL、目标版本、tag/commit、可得摘要、本地 SHA-256、操作者、时间和事务号。无发布方摘要时，不得宣称本地哈希证明发布者身份。
- 备份完成并校验后才能更新；永不删除唯一恢复点。Windows 文件占用、磁盘满、断电/中断均须可诊断。
- 明确提示：代码目录回滚不能完全回滚共享 Python 依赖；发生环境变化时按规划中的保守策略处理。
- 自更新、reserved 插件、未知来源、版本不可解析、AstrBot 不兼容及预发布版本默认阻断。

## 8. 测试要求

- 测试置于 `tests/`，可在插件根目录独立执行 `python -m pytest -q`；框架依赖使用 mock/stub，另设固定 AstrBot 版本的契约/集成测试。
- 覆盖命令解析、配置加载、版本/约束、候选资格、状态机、计划幂等、规则迁移、DST/时区、调度恢复、锁竞争、审计脱敏和 `terminate()`。
- 故障注入覆盖断网、403/429、超时、坏 ZIP、元数据错误、路径逃逸、软链接、磁盘满、复制/删除失败、reload 异常、健康检查失败、回滚失败及进程中断恢复。
- 覆盖 Windows 原生与 Linux/Docker 文件语义、最低支持 AstrBot 版本和 `<5` 范围内选定的最高验证版本。
- 任一事务结束后只能是新版本健康、旧版本健康或明确 `ROLLBACK_FAILED`；不得记录成功但插件不可加载。
- 阶段结束必须运行测试、静态检查（若项目采用）、最小加载验证，并给出命令、结果与未覆盖项；禁止声称未实际运行的测试已通过。

## 9. 禁止事项

- 禁止跳过公共规范、开发规划或阶段门槛；禁止在需求未确认时臆造稳定 AstrBot 私有 API。
- 禁止调用 Dashboard HTTP 来替代同进程适配器；禁止平行复刻官方 ZIP 更新链路，除非有书面决策和完整安全测试。
- 禁止阻塞式网络 I/O、裸 `except`、吞异常、字符串版本比较、无超时请求、无边界删除/覆盖、动态执行不可信文本。
- 禁止默认全选、默认开启自动更新、自动纳入新插件、更新自身、绕过兼容校验或自动处理不可解析版本。
- 禁止提交运行数据、备份、日志、token、缓存、虚拟环境、构建产物、测试临时文件或机器绝对路径。
- 禁止为了“测试通过”削弱断言、删除失败测试或用实现细节 mock 掉核心风险。

## 10. 验收标准

最终版本必须同时满足：公共规范合规；身份和版本一致；在声明范围内加载/卸载干净；只读检查与资格原因准确；手动和定时路径统一；规则跨重启且不重复；更新串行、幂等、可审计；失败可回滚或明确告警；禁用状态保留；自更新与不可信目标被阻断；安全、契约、集成和故障注入测试通过；配置、命令和管理员页面（若目标 AstrBot 支持）可用且有清晰错误反馈；文档与实际目录、配置、命令和行为一致。

完成后逐条给出验收矩阵：要求、实现位置、测试名称、实际结果、证据与残余风险。任何关键项缺失均不得标记“完成”。

- 按阶段提交，小而可审查；建议使用 `docs:`、`test:`、`feat:`、`fix:`、`refactor:`、`security:` 前缀。
- 每次提交前检查 `git diff` 和待提交文件，确认无秘密、运行数据、临时文件或无关格式化。
- 每阶段报告必须列出：固定的 AstrBot tag/commit、变更文件、关键设计决定、迁移影响、执行过的命令与原始结果摘要、失败/跳过项、风险和下一阶段条件。
- 元数据、注册信息、Schema、依赖、代码、测试和文档必须在同一提交序列中保持一致；版本升级遵守语义化版本。
- 未经明确授权不得推送远端、创建发布、改写历史或合并分支。发现规划与框架事实冲突时先停止，提交证据和修订建议，不得带病推进。
